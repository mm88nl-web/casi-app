## Findings

### 1. [HIGH — proven with a test] Predictable `escrow_id` + permissionless `initialize_escrow` lets anyone permanently squat a future booking's PDA before it exists

**What's wrong**: `initialize_escrow`'s PDA is seeded by `[ESCROW_SEED, escrow_id]` only — it does not include the viewer or streamer. `escrow_id` in actual production use is `sha256(String(bookings.id))` (`uuidToBytes()`, `src/lib/casi-escrow.ts:94-99`), where `bookings.id` is a plain Postgres bigint auto-increment column that `POST /api/bookings/create-solana` (`src/app/api/bookings/create-solana/route.ts:182-262`) hands straight back to the caller as `booking_id`. Anchor's `init` (not `init_if_needed`) on `escrow_state` and `vault` means whichever transaction reaches that PDA first owns it permanently. `initialize_escrow`'s `viewer` is any signer and `streamer` is an unchecked, unsigned pubkey of the caller's choosing (already a known/accepted-risk pattern from the prior review) — so nothing stops a third party who has never seen a specific booking from calling `initialize_escrow` themselves against a *predicted future* `escrow_id`, using their own tiny amount of USDC and an arbitrary streamer pubkey.

**Attack scenario**: An attacker creates one throwaway booking of their own (or just watches the public `booking_id` field returned by the create-solana route) to learn roughly where the sequential id counter is, then calls `initialize_escrow` directly against the program (bypassing the web app, its IP rate limit, and its `overlay_elements` ownership check entirely — same reachability the prior review already established for Finding 4) for a range of near-future ids, choosing Flash type. Weeks later, a real viewer's booking lands on one of those ids. The real viewer's own `initialize_escrow` call — for the *same* PDA, because `escrow_id` is a pure function of the id — fails with an "already in use" error. The booking can never get a working on-chain escrow at its correct address, permanently, for a reason entirely outside the real viewer's or streamer's control. Because Flash-type Pending escrows are never reachable by the permissionless `cancel_stale_pending` crank (it only accepts `EscrowType::Beam`), the squat is not even bounded by the 7-day timeout — only the attacker's own signature can ever free it, and they have no reason to.

This is not a fund-theft bug — the attacker only ever spends their own SOL/USDC, and can even reclaim it via `deny_flash`/`approve_flash` and re-squat instantly — but it is a very cheap (~5,000 lamports per id), very durable, pre-emptive denial-of-service on the entire Solana payment rail. A single attacker with a scripted loop could pre-squat a wide contiguous range of future booking ids for a few dollars of SOL and permanently break Solana bookings platform-wide.

**Proof**: `tests/pda-squatting-dos.ts` (new file), both tests passing against a real deployment:
- `"PDA squatting: a third party who only knows a future sequential 'booking id' can permanently deny that booking a working on-chain escrow..."` — attacker squats booking id 7,340,001's PDA with 1 micro-USDC; a "real" viewer's later `initialize_escrow` call for the same id, with a real 5 USDC amount, fails; the PDA is confirmed still owned by the attacker afterward.
- `"confirms the squat is NOT bounded by the 7-day stale-pending timeout..."` — `cancel_stale_pending` against the same Flash-type squat fails with `WrongEscrowType`, at any elapsed time.

Run: `./scripts/test-real-deploy.sh --grep "PDA squatting|WrongEscrowType when the attacker chooses Flash"`.

**Fix direction** (app-layer, not `lib.rs` — the on-chain PDA-per-`escrow_id` design is fine for a generic primitive; the problem is what CASI feeds it): stop deriving `escrow_id` from a low-entropy, publicly-visible sequential integer. Either mint a server-generated random 32-byte nonce per booking (stored alongside `bookings.id`, used only for the PDA seed) or otherwise ensure the value used to derive `escrow_id` is unguessable before the real `initialize_escrow` transaction lands.

### 2. [HIGH — proven; the dead-code half by direct citation, the on-chain severity by a test] The "Revoke" button in Settings never actually revokes anything on-chain

**What's wrong**: `POST /api/solana/delegates/revoke` (`src/app/api/solana/delegates/revoke/route.ts`) only sets `streamer_delegates.revoked_at = now()` — its own doc comment says so explicitly: *"On-chain revoke is a separate streamer-signed tx (`revoke_delegate`) — this route only handles the DB side."* The only caller of this route, `revoke()` in `src/app/studio/_components/DelegateKeyCard.tsx:160-177`, does exactly one `fetch()` to that route and nothing else — no wallet popup, no `CasiEscrowClient` usage, no transaction of any kind. `grep -rn "revokeDelegate\b" src` turns up exactly one hit in the entire application: the method's own definition in `src/lib/casi-escrow.ts:869`. The on-chain `revoke_delegate` instruction is completely unreachable from the shipped product.

Per `lib.rs`, there is no on-chain concept of "revoked" independent of the `StreamerDelegate` account being closed — `session_key` and `expires_at` sit exactly as `set_delegate` left them. So a streamer who clicks "Revoke" — following exactly the affordance the Settings page gives them — has changed nothing about what the session key can do on-chain. It remains fully authorized for up to `MAX_DELEGATE_LIFETIME_SECS` (180 days).

**Attack scenario**: This requires a session-key compromise as a precondition (a `DELEGATE_ENCRYPTION_KEY` leak, a DB read, a backup snapshot — external to this bug), but incident response then fails completely: the streamer clicks Revoke, sees success, and believes they're safe. They are not. Because `cranker` in `SettleBeamDelegated`/`ApproveFlashDelegated`/`DenyFlashDelegated`/`StartBeamDelegated` is an unconstrained `Signer` — anyone willing to pay their own SOL fees can act as cranker, not just CASI's real infrastructure — an attacker who has only the leaked session secret can, with a throwaway self-funded keypair and zero involvement from CASI's servers, force-settle every Active beam that streamer ever runs at (near-)zero streamer payout, or force-deny every incoming flash, repeatedly, for as long as the delegate's on-chain expiry allows. The streamer's own "Revoke" click does nothing to stop this.

**Proof**: `tests/delegate-revoke-app-gap.ts` (new file), passing against a real deployment. Installs a delegate and starts a real 10-USDC, 5-minute Beam the honest way, deliberately does *not* call `revoke_delegate` (matching production `DelegateKeyCard.tsx` exactly), then has an attacker — holding only the session keypair plus a brand-new, self-funded, CASI-unrelated "cranker" keypair — call `settle_beam_delegated` ~1.2 seconds after the beam started. The call succeeds; conservation holds (streamer + viewer = total, so this is a payout-*timing* attack, not a mint bug) but the streamer receives well under 5% of the real payment and the viewer gets the rest refunded; the escrow_state account is fully closed (irreversible); and the delegate PDA is confirmed still fully live afterward with the original `session_key` unchanged.

Run: `./scripts/test-real-deploy.sh --grep "force-zeroes a real streamer"`.

**Fix direction** (app-layer): wire `DelegateKeyCard.tsx`'s `revoke()` to also sign and submit the on-chain `revoke_delegate` instruction (via `CasiEscrowClient.revokeDelegate()`), the same two-phase pattern already used for install/finalize, and don't report success to the streamer until that on-chain step lands. `revoke_delegate` requires the streamer's own signature (no cranker/delegate override in its accounts struct), so this is unavoidably a wallet-signed step — the UI just needs to actually perform it instead of silently skipping it.

### 3. [MEDIUM — the code gap is proven by direct reading; downgraded from an initial worse hypothesis after tracing every consumer; not proven with an executable test] `attach-solana-tx` trusts a client-supplied `tx_signature` and `escrow_pda` with no server-side verification

**What's wrong**: `POST /api/bookings/attach-solana-tx` (`src/app/api/bookings/attach-solana-tx/route.ts:31-65`) authenticates the caller correctly (per-booking `cancel_token`, constant-time compare) but then writes the client-supplied `tx_signature` and `escrow_pda` verbatim — there is no check that `escrow_pda` actually equals `deriveEscrowPda(booking_id)`, and no check that `tx_signature` corresponds to a real, valid on-chain transaction at all. A caller who owns any booking (trivially true for their own, even a $0 one) can set that booking's `tx_signature` to an arbitrary junk string.

I initially suspected this could enable a genuine content/fund hijack — pointing a cheap booking's `escrow_pda` at another viewer's real, already-funded escrow to make `isPaymentConfirmed()` (`!!(tx_signature || ...)`, per `AGENTS.md`) show "paid" and ride their payment. **I traced this all the way through and it does not work as a fund- or content-redirection attack**: every actual money-moving call — `client.startBeam()` (`src/lib/casi-escrow.ts:753-767`), the delegated `start-beam`/`settle-beam` routes (`src/app/api/solana/delegates/{start-beam,settle-beam}/route.ts`, both pass `escrowId: booking.id`, never the stored `escrow_pda` string) — independently re-derives the PDA from `booking.id` via `deriveEscrowPda()`, never trusting the DB column. `approveBooking()` (`src/lib/streamer-moderation.ts:219-226`) also confirms chain success *before* flipping DB status or touching `overlay_elements.image_url`. So a booking with a corrupted `escrow_pda` simply fails cleanly on-chain (`AccountNotInitialized`) when anyone tries to actually start/settle it under its own id — no funds move, no content airs.

I also checked whether the DB-column corruption could still cause harm via the Helius webhook, which matches incoming on-chain events to rows by `escrow_pda IN (...)` with `.limit(1)` and no tie-break (`src/app/api/webhooks/solana/route.ts:178-191`) — two rows sharing a PDA could, non-deterministically, misattribute a real event's `overlay_elements.image_url` mirror to the wrong row. This *would* be a moderation-bypass path, but it requires the attacker to first learn another viewer's still-**Pending** booking's `escrow_pda` (the only state where the mis-attribution would let `start_beam`-flavored events do anything). I checked the current RLS policy for this directly: `supabase/migrations/20260827010000_narrow_anon_select_policies.sql` (applied 2026-08-27, one day before this review) restricts anon `SELECT` on `bookings` to `status IN ('active','approved_queued')` or `(solana AND status IN ('denied','expired') AND escrow_pda IS NOT NULL)` — **Pending rows' `escrow_pda` are no longer publicly readable**. That closes the practical path to the scarier version of this bug, as of a very recent, unrelated hardening pass.

**What remains real today**: a caller can still fake their own booking's "paid" badge with a junk `tx_signature`, with no on-chain proof required. The practical impact is bounded to spoofed UI state / streamer-queue clutter (a fake "paid, ready to approve" entry that then errors harmlessly on real approval) — not fund loss or unauthorized content — but it's still a real validation gap, and relying on the *current* narrowness of an unrelated RLS policy as the only thing standing between this and a worse outcome is fragile (a future RLS change, a realtime-subscription leak I did not audit, or a to-be-added authenticated cross-streamer view could reopen the Pending-row visibility this currently depends on).

**Proof**: not executed as a runnable test — this requires a live Next.js + Supabase harness that doesn't exist in the current test infrastructure (all existing tests are pure Anchor/localnet). The "it can't redirect funds" half is proven by direct code citation of every consumer of `booking.escrow_pda` (listed above); the "Pending rows aren't anon-readable" half is proven by reading the actual, currently-applied migration SQL, not by inference.

**Fix direction** (app-layer): have `attach-solana-tx` independently re-derive the expected `escrow_pda` from `booking_id` server-side and ignore/reject a client-supplied value that doesn't match, and verify `tx_signature` actually exists on-chain (e.g. `connection.getTransaction`) and references the derived PDA before trusting it — the same spirit as the amount-integrity check the webhook already does for `initialize_escrow`.

### 4. [LOW / informational — suspected, not verified with a test] `TransferHookNotAllowed` is checked once at `initialize_config` time, never again

`initialize_config`'s TransferHook rejection (now fixed for the constant/offset bugs described in my task brief) only runs when the deployer calls `initialize_config`. Token-2022's TransferHook extension supports a retained update authority that can attach a hook program to a mint *after* it passes this check — the program has no mechanism to re-verify `accepted_mint` at any later point (`initialize_escrow` just requires `usdc_mint.key() == config.accepted_mint`, with no extension re-check). For CASI's actual deployment this is moot in practice: real USDC is a classic 82-byte SPL Token mint with no extension data at all, so the whole TLV-parsing block never executes. It matters for the "generic reusable primitive, other teams fork and deploy" framing the grant narrative leans on — a team using a Token-2022 stablecoin with a live hook-update authority could have a safe mint turn unsafe post-launch with no way for the program to notice. Not tested — would require standing up a Token-2022 mint with a retained TransferHook update authority and exercising the update instruction, which felt disproportionate given it doesn't threaten CASI's own capped-mainnet plan specifically. Flagging for awareness, not urgency.

### 5. [LOW / informational — suspected, not verified with a test] `GlobalConfig.min_escrow_amount`/`max_escrow_amount` aren't validated against each other

Neither `initialize_config` nor `update_config` checks `min_escrow_amount <= max_escrow_amount`. If both are ever set nonzero with min > max (an admin fat-finger, not an attacker-triggerable path — only the admin key can call either instruction), `initialize_escrow`'s two independent `require!` checks become mutually unsatisfiable and **no amount at all** would ever pass, silently taking new-escrow creation offline platform-wide until the admin notices and corrects it. Purely a robustness/input-validation suggestion, not a security finding in the adversarial sense — no external caller can trigger it.

## Checked and found clean

- **Fund redirection via `attach-solana-tx`'s corrupted `escrow_pda`.** Traced every consumer of `booking.escrow_pda` in the money-moving path (`casi-escrow.ts`'s `startBeam`/`buildStartBeamDelegatedIx`/`buildSettleBeamDelegatedIx`, both delegated routes, `streamer-moderation.ts`'s `startSolanaBeamOnChain`) — all of them re-derive the PDA from `booking.id`, none of them trust the stored string for signing. See Finding 3's writeup for the full trace.
- **RLS on `bookings` UPDATE.** An older migration (`20260418100000_tighten_bookings_rls.sql`) once had a permissive `bookings_update_anon` policy gated only by status, not caller identity — but a later migration (`20260422000000_revoke_anon_booking_update.sql`) fully revokes `UPDATE (status)` from `anon` and drops that policy, matching `AGENTS.md`'s current claim that anon cannot UPDATE bookings at all. Confirmed by reading the actual migration files in dependency order, not by trusting the doc.
- **Streamer-side moderation authorization boundary.** `bookings_update_streamer` (same migration) correctly scopes UPDATE to `auth.uid() = profile_id` — `streamer-moderation.ts` writing directly via the streamer's browser Supabase client is not a hidden IDOR, RLS is the enforcement layer and it's correctly scoped.
- **Delegate route authorization.** All five `delegates/*` routes I read in full (`approve-flash`, `deny-flash`, `settle-beam`, `start-beam`, `install`, `revoke`, `status`) consistently gate on `booking.profile_id === user.id` / `flash.profile_id === user.id` after a real Supabase bearer-token check, before touching any session key or on-chain call.
- **Helius webhook authentication.** Constant-time shared-secret comparison (`timingSafeEqual`), correctly returns 200 either way (so Helius doesn't retry-storm on a bad actor), and the amount-integrity check for `initialize_escrow` (2026-08-10 Finding 1's fix) is real and functioning.
- **`cancel_token` comparisons** in `attach-solana-tx` and `viewer-deny` use `timingSafeEqual` with a length check first — not vulnerable to a timing side-channel.
- **Chain-before-DB-flip ordering.** Every code path I checked in `streamer-moderation.ts` (`approveBooking`'s direct-start branch, the queue-promotion branch inside `endBeamEarly`) confirms on-chain success before ever flipping `bookings.status` or writing `overlay_elements.image_url` — a failed on-chain call leaves the row in a safely-retryable state, it never shows unapproved/unfunded content.
- **`cron/solana-reconciler` and `cron/cranker-monitor`** — constant-time `CRON_SECRET` checks, idempotent status-guarded writes, the monitor is read-only.
- **`webhooks/pumpfun`** — genuinely inert: no DB writes, no auth, pure logging. Not wired to anything money-related.
- **On-chain settle-math, account-substitution, and reentrancy classes** — not independently re-tested this session (unchanged from the 2026-08-10 review, which proved these directly); I read the same `lib.rs` sections again with fresh eyes looking for a new angle and didn't find one.

## What this review can and can't substitute for

This was a second, independent AI-driven pass, not a professional audit, and not a replacement for the external Sec3/OtterSec/Neodyme-caliber review already planned. It found two new, cleanly-provable issues (the PDA-squatting DoS and the dead revoke button) that I'd expect a paid audit to also catch, plus one real-but-narrower app-layer gap (Finding 3) that I want to be honest was scarier in my first pass than it turned out to be once I actually traced the code — which is itself the point of "prove, don't speculate": my first hypothesis for Finding 3 would have overstated the severity if I'd reported it without checking every downstream consumer and the very recent RLS migration.

What I did not do: a live end-to-end test of Finding 3 (needs a running Next.js + seeded Supabase instance, out of scope for the Anchor test harness this review otherwise used); a live Token-2022 TransferHook-update PoC for Finding 4; a review of Supabase Realtime's channel-level RLS enforcement (I verified table-level RLS via migration history, not whether a realtime subscription could leak Pending-row data through a different code path); fuzzing beyond the two hand-built attack scenarios; or any devnet/mainnet transactions. My working environment's `lib.rs` was, for reasons unrelated to my own work (disclosed above), on an older revision than the one my task brief describes as current — I did not need to and did not re-verify the 3 bugs that brief says were already found and fixed elsewhere, since neither of my new findings depends on that code path.

Treat the two HIGH findings as things to fix before real money is at stake on the Solana rail: the PDA-squatting DoS can take down the whole payment rail for pennies, and the dead revoke button means the product's only advertised incident-response mechanism for a compromised session key does not work. Finding 3 is worth closing as defense-in-depth even though its currently-reachable impact is limited to UI-state spoofing, precisely because that "currently limited" status depends on an RLS policy that could change for unrelated reasons.
