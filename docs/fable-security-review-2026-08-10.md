# CASI Escrow — preliminary AI security review

**Reviewer**: Fable 5 (Claude Agent), acting under the owner's authorization as a defensive review of their own product.
**Date**: 2026-08-10
**Program reviewed**: `programs/casi-escrow/src/lib.rs` @ `declare_id!("CDunHmMe2KW8qmjoqWanuu3p1DsEYjqRA1yVmyXDtakM")`, ~1905 lines, Anchor 0.31.1.
**Scope**: on-chain program + the client/server TypeScript that talks to it (`src/lib/casi-escrow*.ts`, `src/lib/cranker-keypair.ts`, `src/lib/solana-network.ts`, `src/lib/rate-limit.ts`, `src/lib/delegate-crypto.ts`, `src/lib/streamer-moderation.ts`, and the `src/app/api/{bookings,solana,webhooks,cron,admin}` routes that touch the escrow).

## What was checked and how

I read the design docs first (`README.md`, `PRIMITIVE.md`, `FEE_MODEL.md`, `DEPLOY.md`, `escrow-state.md`, `capped-mainnet-plan.md`, `AGENTS.md`) to check implementation against stated intent rather than guessing intent from code. I then read the full program (all 12 instructions, 3 account types, error enum), the TS client wrapper, the raw byte-offset decoder, the cranker keypair loader, and every server route that builds or verifies an escrow transaction (webhook, reconciler cron, the four `delegates/*` routes, `bookings/create-solana`, `admin/init-escrow-config`, `flashes/moderate`). Per the owner's mid-task correction, I then switched from "check code against its own claims" to an attacker mindset: for every instruction I asked what a malicious viewer, malicious streamer, or permissionless caller could construct, and where I had a concrete hypothesis I built it as a runnable Anchor/TypeScript test against a local validator rather than just describing it. All work stayed on localnet — no devnet/mainnet RPC, no mainnet keypair, no real funds, and `programs/casi-escrow/src/lib.rs` and `tests/casi-escrow.ts` were not modified.

**`anchor test` does not currently pass cleanly.** A first clean run produced `96 passing / 33 failing`, with every failure an `AccountNotInitialized` error on the `config` account inside `initialize_escrow`. Root cause, confirmed by directly comparing two local deployments: the version of the program `anchor test` spins up (via `solana-test-validator --bpf-program`, genesis-loaded with "upgrades disabled") reports its ProgramData upgrade authority as `Some(11111111111111111111111111111111)` — the System Program's all-zero address — rather than `None`. `initialize_config`'s authority check (`programs/casi-escrow/src/lib.rs:117-123`) only handles `has_authority == 0` (immutable, any signer OK) or `has_authority == 1` with a real matching key; it has no branch for "`Some` but the address is unsignable," so on the standard `anchor test` harness `initialize_config` can never succeed for *any* signer, and every downstream `initialize_escrow` call fails. `tests/casi-escrow.ts` never calls `initialize_config` anywhere — this is very likely why, and it means the suite has probably never actually run end-to-end for whoever last touched it either. I confirmed the diagnosis by deploying the identical bytecode via a normal `solana program deploy` (not genesis-loaded) to a fresh local validator: authority then correctly reads back as the deployer's real pubkey, `initialize_config` succeeds, and I then ran a new, self-contained test file (`tests/security-findings.ts`) against that validator — **6 of 6 new attack-PoC tests passed** (5 defenses held, 1 test proved a real cost-asymmetry attack works, described below). I did not edit `tests/casi-escrow.ts` or `lib.rs`.

## Findings

### 1. [HIGH — value integrity] Escrowed amount is never checked against the price the streamer was shown

**What's wrong**: `initialize_escrow` (`programs/casi-escrow/src/lib.rs:283-350`) accepts any caller-chosen `amount` bounded only by `GlobalConfig.min/max_escrow_amount` — it has no concept of "the price this slot is supposed to cost," which is correct for a generic primitive. The problem is that nothing downstream ever reconciles that free-form amount against the price the app displayed to the streamer:

- The Helius webhook's `initialize_escrow` handler (`src/app/api/webhooks/solana/route.ts:203-256`) stamps `tx_signature` and `viewer_wallet` on the booking the moment *any* successful `initialize_escrow` lands — it never reads or stores the instruction's `amount`.
- The client-side Approve gate, `isPaymentConfirmed()` (`src/app/studio/page.tsx:94-101`, mirrored logic implied for `/admin`), only checks `!!(b.payment_intent_id || b.tx_signature || ...)` — presence of a signature, not its value.
- `approveBooking()` (`src/lib/streamer-moderation.ts:186-244`) calls `startSolanaBeamOnChain(ctx, booking)` (line 224) purely gated on DB `status`, with no amount check anywhere in between.
- `src/lib/casi-escrow-decoder.ts` — the "raw byte-offset decoder for EscrowState" — never actually decodes `total_amount` (offset 136-144); it's discriminator-matching only, so nothing downstream is even wired to look at the true amount.

**Attack scenario**: A viewer books a beam through the normal UI (so the DB row gets the streamer's real configured price, e.g. $50, in `bookings.price_value`), but instead of letting the SDK sign `initialize_escrow` with the matching `amountUsdc`, they sign it themselves (the program ID, IDL, and TS client are all public/Apache-2.0) with `amount = 1` (1 micro-USDC). The webhook still marks the booking "paid" (a `tx_signature` exists), `isPaymentConfirmed()` still returns true, and the streamer — especially one using the no-popup delegated-approve flow — sees a normal-looking "$50 beam, paid" request and approves it. The viewer gets their full-duration slot for 0.000001 USDC instead of $50. This is not a bug in the on-chain program (a neutral primitive correctly has no price opinion) — it's a missing reconciliation step in the app layer that trusts client-supplied on-chain data without checking it, exactly the class of bug the review brief called out.

**Proof**: `tests/security-findings.ts`, "Trust gap" describe block — a Beam funded with `amount = 1` goes through the identical `initialize_escrow` → `start_beam` → `settle_beam` lifecycle as a real payment, indistinguishable at every step except the number. Passed.

**Fix direction (not applied — app-layer, not `lib.rs`)**: have the webhook or the approve path fetch `escrow_state.total_amount` (already in the account, already in the `EscrowInitialized` event) and reject/flag bookings where it doesn't match `price_value` within a tolerance, before treating `tx_signature` presence as "paid."

Covered in detail above. Restating the severity: `README.md` documents "18 test cases," `DEPLOY.md` says "Run the test suite... All phase-3 tests are in `tests/casi-escrow.ts`," and the grant narrative leans on this coverage. **File:line**: `programs/casi-escrow/src/lib.rs:110-126` (authority-parsing gap), `tests/casi-escrow.ts` (no `initialize_config` call anywhere in the file).

### 3. [HIGH — spam/DoS, proven] Whoever processes a stranger's escrow pays real SOL rent disproportionate to the escrow's value — the shared cranker can be cheaply drained

**What's wrong**: `SettleBeam`'s `streamer_ata`/`viewer_ata` (`programs/casi-escrow/src/lib.rs:1380-1396`, `payer = caller`), `SettleBeamDelegated`'s and `ApproveFlashDelegated`'s ATAs (`payer = cranker`, lines 1510-1519, 1579), `DenyFlashDelegated`'s `viewer_ata` (`payer = cranker`, line 1638), and `CancelStalePending`'s `viewer_ata` (`payer = cranker`, line 1683) all use `init_if_needed` funded by whichever account is bound to `caller`/`cranker` — not by the escrow's own funds, and not by the party who benefits from the new ATA. Any time the counterparty's token account doesn't already exist, whoever processes the escrow eats a real ~2,039,280-lamport (0.00204 SOL) rent-exempt deposit, regardless of how small the escrow itself is.

**Attack scenario, proven with a live PoC** (`tests/security-findings.ts`, "force a disproportionate SOL cost" test): a Beam funded with 100 micro-USDC (0.0001 USDC — deliberately dust) between a fresh viewer wallet and a streamer pubkey that has never held a token account before. After `duration` elapses, a third-party crank caller settles it (the permissionless post-duration path CASI's own design intends anyone to be able to use). Reading the confirmed transaction's own ledger record (`meta.preBalances`/`postBalances`, not a racy follow-up RPC call — see note below), the caller's account lost exactly 2,039,280 lamports — over a million times the value of the escrow it processed. `CancelStalePending` uses the identical `init_if_needed, payer = cranker` pattern for `viewer_ata`; I could not directly time-warp the real 7-day `PENDING_TIMEOUT_SECS` on a live-clock local validator, but the accounts-struct mechanism is identical, so the same per-call cost applies to CASI's actual production cranker path (the daily reconciler's automatic `cancel_stale_pending` crank).

Per `DEPLOY.md`, the production cranker is funded with only ~0.05 SOL. **~0.05 / ~0.00204 ≈ 24** such escrows (each costing the attacker only a Solana base fee plus 1 micro-USDC of token, which they get back in full when the escrow settles or the crank refunds them) would exhaust it entirely. Compounding this: `initialize_escrow`'s `streamer` field is an `UncheckedAccount` (`programs/casi-escrow/src/lib.rs:1153`) with **no signature or consent requirement** — I proved this directly (see Finding 4) — so an attacker doesn't need any real streamer's cooperation, doesn't need to go through `/api/bookings/create-solana` (so its IP rate limit and `overlay_elements` ownership checks are irrelevant), and can target any pubkey they like, including a real onboarded streamer.

**Impact if it lands**: not fund theft — the worst outcome is the shared cranker running dry, at which point (per the code's own design, `src/lib/cranker-keypair.ts` and the `/api/solana/delegates/*` 503 fallback) every streamer's delegated approve/kick flow degrades to a wallet-popup-per-action, i.e. a platform-wide UX regression until someone notices (the daily `cranker-monitor` cron) and refills it. Rated HIGH rather than MEDIUM because it is fully proven, cheap, automatable, and the resulting outage affects every streamer using the no-popup flow simultaneously, not just the targeted one.

**Note on methodology**: my first attempt at this PoC read `getBalance()` before/after and saw a false "$0 spent" because a follow-up `getBalance` call on this local validator lagged the transaction that had already confirmed. I caught this by cross-checking against the transaction's own `preBalances`/`postBalances`, which is the authoritative ledger record and is what the final, passing test asserts on. Flagging this because it's exactly the kind of false-negative a less careful check would have missed and reported as "no cost, not exploitable."

### 4. [MEDIUM — spam/DoS, proven] Escrows can be opened against any pubkey with zero consent or signature from the target

**What's wrong**: `InitializeEscrow`'s `streamer` account (`programs/casi-escrow/src/lib.rs:1153`) is declared `UncheckedAccount<'info>` with no `Signer`, ownership, or existence constraint — by design, since the streamer only needs to act *later* (`start_beam`/`approve_flash`), not at deposit time. But this means anyone can create a `Pending` escrow "targeting" a `streamer` pubkey that never signs, never consents, and may not even be a real user.

**Proof**: `tests/security-findings.ts`, "open Pending escrows against a target who never signs anything" — a fresh, never-airdropped, never-signing keypair is used as `streamer` in a real `initialize_escrow` call from the attacker's own funded viewer wallet; it succeeds and the resulting `EscrowState.streamer` field matches the victim pubkey exactly. Passed.

**Impact**: standalone this just means an attacker can litter arbitrary pubkeys with tiny Pending escrows (recoverable by the attacker via self-`cancel_escrow`, or by anyone via `cancel_stale_pending` after 7 days — no theft). Its real significance is as the enabling step for Finding 3: it means the cost-asymmetry attack doesn't require compromising or tricking a real streamer, and doesn't go through any app-layer surface (`/api/bookings/create-solana`'s rate limit, `overlay_elements.profile_id` check, or the capped-mainnet plan's streamer whitelist) — it's reachable by calling the Anchor program directly with public tooling.

### 5. [MEDIUM] The cranker-spend rate limit protecting against a self-dealing streamer is per-process, not distributed

**What's wrong**: `src/lib/rate-limit.ts` is explicit in its own header comment that `inMemoryRateLimit` "buckets live in the lambda's process memory... is NOT shared across concurrent serverless instances" and is "a deterrent against a single hot caller, not a hard distributed guarantee." It's used as the *only* defense in all four `delegates/*` routes (`settle-beam/route.ts:90`, `start-beam/route.ts:85`, `approve-flash/route.ts:80`, `deny-flash/route.ts:75`) against exactly the scenario `settle-beam/route.ts`'s own comment names: "a malicious streamer can't self-deal (fund + approve + settle their own beams in a loop) to drain [the cranker's] SOL." On Vercel, concurrent/fanned-out requests can land on different execution environments, each with its own empty rate-limit bucket, so a streamer (or anyone who compromises a streamer session) willing to fire requests in parallel rather than serially has a real chance of exceeding the intended 60-ops/60s cap before any single bucket saturates.

**Severity note**: this only matters for an *authenticated* streamer (or someone holding their session) self-dealing against their own bookings — it requires an account takeover or a genuinely malicious streamer, not an anonymous viewer — which is why this is MEDIUM rather than HIGH. But it's the only thing standing between that actor and the same cranker-drain outcome as Finding 3, achieved without even needing the ATA-freshness trick.

**Fix direction**: a DB-backed or Redis-backed counter, as the file's own comment already suggests.

### 6. [MEDIUM] Deployed config has `min_escrow_amount = 0`, disabling the program's own documented anti-griefing floor

**What's wrong**: `GlobalConfig.min_escrow_amount`'s doc comment (`programs/casi-escrow/src/lib.rs:1716-1719`) explains its purpose is to "make ATA-rent griefing uneconomical... each deny costs the streamer ~0.002 SOL to init the viewer ATA." The actual deployed-config call site, `src/app/api/admin/init-escrow-config/route.ts:131`, calls `initializeConfig(new BN(0), new BN(0))` — both cap and floor set to zero, i.e. no minimum at all. This directly widens the blast radius of Findings 3 and 4: the program's own designed-in mitigation for exactly this class of attack is currently turned off in the actual deployment. Since `update_config` (admin-only) can raise `min_escrow_amount` at any time without a program change, this is trivially fixable at the config layer, but is worth flagging because it's not merely "not yet configured" — it's live at the value the code comment specifically warns against.

### 7. [LOW] No test coverage at all for `approve_flash_delegated`, `deny_flash_delegated`, or any `GlobalConfig` instruction

`tests/casi-escrow.ts` has zero cases for `initialize_config`, `update_config`, `transfer_admin`, the pause gate, the min/max cap enforcement, or — most notably — the hand-rolled Token-2022 TransferHook TLV parser at `programs/casi-escrow/src/lib.rs:148-176` (manual byte-offset walking of extension data, exactly the kind of code that's easy to get subtly wrong and hard to eyeball-verify). It also has no coverage for the delegated Flash twins (`approve_flash_delegated`/`deny_flash_delegated`), even though the wallet-signed `approve_flash`/`deny_flash` are tested. None of this is a demonstrated bug — I did not find a way to break the TLV parser or the config gates in the time available — but it's a real coverage gap an external auditor will also flag, and it's cheap to close before that audit starts.

## Checked and found clean

- **Account substitution / `has_one` enforcement on `settle_beam`.** Tried two variants: (a) a permissionless post-duration caller passing its own pubkey as both `streamer` and `viewer` to redirect the payout to itself, (b) trying to settle escrow A's `escrow_state` PDA while supplying escrow B's `streamer`/`viewer` (a richer, tempting target). Both rejected with `Unauthorized` / a constraint mismatch before any transfer occurred; vault balances were provably untouched afterward. `tests/security-findings.ts`, "account substitution" describe block, both tests passed.
- **Vesting-math rounding direction (`settle_beam`, `settle_beam_delegated`).** `streamer_amt = floor(total * vested_ticks / duration)`, `refund = total - streamer_amt` via `checked_sub`. Tested a non-exact division (total=10, duration=3, settle mid-second) — conservation holds exactly and the streamer's share is always the floor, never the ceiling; the rounding remainder always goes to the viewer's refund, never lets a streamer or a timing-savvy caller claim more than their true proportional share. Separately, the `u128` intermediate in `(total as u128) * (vested_ticks as u128)` cannot overflow for any `u64` inputs — the product of two values ≤ `u64::MAX` is always ≤ `u128::MAX` — so this class is structurally closed, not just empirically clean.
- **Reentrancy via CPI.** Not applicable to this program's design: the two CPI targets (`token_interface::{transfer_checked, close_account}`, associated-token-program) are trusted, non-attacker-suppliable programs, and Solana's CPI model has no fallback/callback hook on a plain SPL transfer the way EVM reentrancy does. The one place a malicious CPI target *could* matter — a Token-2022 mint with a TransferHook extension — is explicitly rejected at `initialize_config` time via the TLV parser (lib.rs:134-176), and `accepted_mint` is immutable afterward, so this is closed structurally once config is set with a safe mint. I did not build a live Token-2022-hook PoC (would require standing up a separate hook program) — this is inference from code reading plus the immutability guarantee, not an executed test.
- **Session-key/delegate scope** (`escrow-state.md`'s "worst case: forced early settle, no theft" claim). Confirmed true by code: `start_beam_delegated`/`settle_beam_delegated`/`approve_flash_delegated`/`deny_flash_delegated` all bind their payout/status-change targets to `escrow_state.streamer`/`escrow_state.viewer` via `has_one`, with no caller-suppliable redirect, and `delegate.streamer`/`delegate.session_key` are bound to the specific PDA seed and session signer via `constraint =`. Three of the pre-existing `SessionDelegate` tests (install/rotate/revoke, expiry-in-the-past, expiry-beyond-max-lifetime) don't require an escrow and so were unaffected by Finding 2 — they ran and passed in the standard `anchor test` harness. The cross-streamer and mismatched-session-key rejection tests for `start_beam_delegated`/`settle_beam_delegated` *do* require an escrow and were among the 33 broken cases; I was not able to independently re-execute those specific negative tests this session (time-boxed after the deeper Finding-3 investigation). I'm inferring they hold, based on identical `has_one`/`constraint =` machinery to the substitution attack I did prove fails elsewhere — but flagging this as inferred, not independently re-verified, rather than overclaiming.
- **Double-settle / double-cancel / reinit-after-close.** `escrow_state` and the vault both close within the same instruction via Anchor's `close =` and the explicit `pda_close_account` call; a closed PDA's address can be reused by a later `initialize_escrow` with the same `escrow_id`, but that always starts a genuinely fresh, zero-balance vault — there's no window to replay or double-spend the old balance. Verified via code reading plus the account-substitution PoC exercising the same close mechanics; the dedicated "rejects double-approve" / "rejects settle_beam twice" cases in the pre-existing suite are among the 33 currently-broken-by-Finding-2 cases and weren't independently re-run.
- **Clock/timestamp manipulation.** `Clock::get()` reads the validator-verified sysvar, not an attacker-suppliable value; `elapsed = now.saturating_sub(start_ts).max(0)` and `vested_ticks = elapsed.min(duration)` structurally prevent negative or over-100% vesting regardless of when a transaction lands.
- **Fee-model correctness.** `FEE_MODEL.md` is explicitly "design only, not implemented" — there is no fee-splitting code in `lib.rs` to check yet. Current behavior (100% direct viewer→streamer) matches `README.md`/`PRIMITIVE.md`'s claim; nothing to flag.

## What this review can and can't substitute for

This was a single AI-driven pass, not a professional audit — it's meant to catch obvious, cheap-to-find issues and give the owner more confidence for the *capped* mainnet trial already planned in `capped-mainnet-plan.md` ($50/booking, $500/streamer TVL, specifically sized so a worst-case incident is bounded because the program is unaudited), not to certify the program safe for uncapped real money. I found and proved two real issues (the price-integrity gap and the cranker cost-asymmetry) that a $22k Sec3/OtterSec/Neodyme-caliber audit would very likely also catch, plus one significant process finding (the broken test harness) that's arguably more useful to know before an audit starts than after. I did not do: formal verification, fuzzing beyond the hand-picked cases above, a review of the Supabase RLS/grants layer beyond what touches the escrow, or anything requiring devnet/mainnet transactions. The delegate cross-streamer rejections and the double-settle/reinit protections are inferred sound from code symmetry with tests I did run, not independently re-executed end-to-end this session — that gap, plus Finding 7's coverage holes, are exactly the kind of thing a real auditor's checklist would close. Treat this as a reason to fix the two proven issues and fix the test harness before the capped launch, not as a green light on its own.
